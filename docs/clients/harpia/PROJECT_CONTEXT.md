## 9. Arquitetura operacional dos bots

### Princípio geral

Bot não deve existir apenas para enviar mensagens. Cada fluxo deve resolver uma dor operacional e terminar com estado claro no CRM.

Todos os caminhos precisam fechar. Nunca deixar:

- bloco sem saída operacional;
- pausa sem destino;
- ramificação sem `nextBlockId` válido;
- início de outro SalesBot/Agente IA sem um `encerrar-bot` depois;
- lead parado no meio de uma automação.

### Linguagem

- Copy deve parecer escrita por **corretor/vendedor de imóveis**, respeitando o posicionamento mais consultivo/patrimonial da Hárpia quando pertinente.
- Não expor ao cliente ações internas de CRM.
- Não dizer frases como:
  - “encaminhei para o responsável”;
  - “seu contexto ficou registrado”;
  - “distribuí seu lead”;
  - qualquer explicação sobre tags, funis, responsáveis, automação ou agente interno.
- Fazer perguntas naturais e comerciais.
- Evitar excesso de “digite 1, digite 2”.

## 10. Bot de primeiro atendimento — regra aprovada

Objetivo: receber rapidamente, identificar origem, coletar o mínimo necessário, distribuir internamente o lead e encaminhar para humano ou IA.

### Fonte do lead

O fluxo deve consultar a **origem real do lead** antes de começar o atendimento principal.

- WhatsApp → segue para o bot de recepção WhatsApp.
- Instagram → inicia o SalesBot específico do Instagram e depois encerra o bot atual.
- Outras origens → tratar conforme configuração definida no ambiente; nunca inventar origem.

As origens reais da MktOn usam referências do workspace, por exemplo WhatsApp/Instagram vinculados às conexões cadastradas. Não inventar IDs de origem em arquivo reutilizável.

### Atendimento

Primeiro atendimento deve ser curto: **máximo 3 a 4 interações relevantes** antes de encaminhar.

Sequência recomendada atual:

1. perguntar nome;
2. identificar necessidade principal;
3. fazer uma qualificação curta;
4. perguntar se pode fazer uma ligação rápida.

A identificação de necessidade deve comportar o portfólio real da Hárpia, incluindo compra, locação, venda/captação, assessoria jurídica, arquitetura, reforma/obras, flipping, gestão patrimonial e futuras frentes de leilão/investimentos.

### Distribuição

- Usar **round-robin/roleta** para distribuir entre **4 corretores**.
- Cada saída da roleta deve executar **Mudar responsável**.
- Distribuição é interna e invisível para o cliente.
- Não criar várias notas repetidas para cada corretor.

### Saída para humano

Se o lead aceitar ligação:

1. mudar etapa/status do lead;
2. criar tarefa de ligação para o responsável quando aplicável;
3. mensagem comercial curta ao lead;
4. `encerrar-bot`.

### Saída para IA

Se o lead preferir continuar por mensagem/não quiser ligação:

1. mudar etapa/status do lead;
2. iniciar Agente IA apropriado;
3. `encerrar-bot`.

O agente IA não deve ser inventado se ainda não estiver criado/configurado. Deixar o bloco para seleção/configuração posterior quando necessário.

## 11. Regra obrigatória para pausas e timeout

Sempre que o bot aguardar resposta do cliente, deve existir também caminho para **não resposta**.

Padrão:

- `msg-recebida` → fluxo de resposta;
- `cronometro` → continuação da régua/reativação.

Nenhuma pausa aguardando cliente pode ficar sem timeout quando existe continuidade automática esperada.

### REGRA APROVADA — não usar “até iniciar expediente” como pausa intermediária automática

**Não inserir uma pausa “até iniciar expediente” logo depois de uma pausa de cronômetro apenas como proteção de horário.**

Esse padrão foi reprovado porque gerou blocos intermediários desnecessários e pontas sem conexão.

Quando a cadência já estiver calculada para horários adequados:

`mensagem → pausa (resposta OU cronômetro) → próxima mensagem/ação`

A saída do cronômetro deve apontar **diretamente** para o próximo bloco previsto.

Só usar um recurso de janela/expediente quando houver necessidade real, schema confirmado e conexão completa de entrada e saída. Nunca criar esse bloco apenas por precaução.

## 12. Follow-up / reaquecimento

Objetivo: recuperar leads que saíram do primeiro atendimento sem avançar.

### Cadência

- Janela aproximada: **20 dias**.
- Quantidade desejada: **9 a 14 mensagens**.
- Estratégia atual preferida: cerca de **12 mensagens**.
- Primeiros 3 dias com maior pressão, incluindo possibilidade de mais de uma mensagem no mesmo dia.
- Depois espaçar em dias alternados/intervalos maiores.
- Toda resposta deve interromper a cadência automática.

### Classificação da resposta

Quando o lead responde, entender intenção antes de continuar:

#### Quer continuar atendimento

- interromper follow-up;
- ajustar tag/status conforme necessário;
- iniciar **Agente IA de Follow**;
- `encerrar-bot`.

#### Quer pausar / deixar para mais tarde

- interromper follow-up;
- executar `mudar-status-lead` preparado para o usuário selecionar manualmente a etapa **Reativação de Base**;
- `encerrar-bot`.

#### Quer parar mensagens / encerrar

- interromper follow-up;
- registrar tag adequada;
- fechar conversa quando essa for a regra definida;
- `encerrar-bot`.

#### Não respondeu toda a régua

- executar `mudar-status-lead` para a etapa de **Reativação de Base**;
- `encerrar-bot`.

Não iniciar automaticamente o bot de reativação de base nesse ponto se a orientação vigente for apenas mover a etapa. A configuração exata da etapa poderá ser feita manualmente no ambiente.

## 13. Reativação de base

É uma frente separada do follow-up de 20 dias.

- Recebe leads que pediram pausa ou ficaram frios após a régua.
- Deve trabalhar uma pausa mais longa antes da nova tentativa.
- Fluxo e cadência ainda serão definidos em etapa própria.

## 14. Regras permanentes de criação/revisão de SalesBot

Antes de entregar qualquer arquivo `.mktonbot.json`:

- usar schema real da MktOn;
- consultar código quando houver dúvida de `kind`, ação ou propriedade;
- validar `startBlockId`;
- validar todos os `nextBlockId`;
- validar IDs duplicados;
- validar todas as saídas de `condicao`, `validacao`, `round-robin` e `pausar`;
- validar que todo `iniciar-salesbot` e `iniciar-ia` possui continuação para `encerrar-bot`;
- garantir que somente blocos terminais intencionais fiquem sem saída;
- não criar notas repetidas para configurações equivalentes;
- se o owner pedir para não usar notas naquele bot, não criar nenhuma;
- mudança de etapa deve existir como bloco `mudar-status-lead` mesmo quando o destino final depender de seleção manual;
- não inventar pipelines/etapas;
- layout deve ser legível como organograma;
- toda pausa de resposta deve ter caminho coerente de timeout;
- **não criar pausa intermediária “até iniciar expediente” sem necessidade real e sem conexão integral**;
- copy deve ser comercial e natural para o segmento imobiliário;
- nunca expor ao cliente detalhes internos do CRM.

### Checklist de fechamento estrutural

Antes de entregar:

- [ ] zero referências quebradas;
- [ ] zero pontas soltas não intencionais;
- [ ] todas as pausas possuem todas as saídas conectadas;
- [ ] todas as ramificações chegam a outro bloco válido;
- [ ] todo caminho operacional termina em `encerrar-bot` ou em continuação explicitamente prevista;
- [ ] não existe pausa intermediária sem função comercial/técnica real;
- [ ] respostas do lead interrompem cadências quando necessário.
